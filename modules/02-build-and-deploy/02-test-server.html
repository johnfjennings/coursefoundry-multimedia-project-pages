2. Optional: create a test server on AWS

Author

Mr. John Jennings

NoteThis step is optional

Your lecturer has already built your team’s test server, and your team’s merges deploy there without this step. To find your team’s site, see Finding your team’s sites.

Do this step if you want to learn how the server behind it is set up. You build your own server for your own practice copy of the repo, so nothing you do here affects your team.

Who: you, on your own, in your own AWS Academy lab. Goal: an EC2 instance running Docker, MySQL and a GitHub runner labelled test, which deploys the develop branch of your practice repo.

2.0 Make a practice copy of the repo

Warning

Never register a runner in your team repo. Your lecturer’s server already serves it, and a second runner with the same label would take some of your team’s deployments.

  1. On GitHub, click + → New repository. Name it gallery-practice, make it Private, and leave Add a README, .gitignore and license unset, so it is empty. Click Create repository.

  2. On your laptop, in a folder outside your team clone, copy every branch and tag of the team repo into it:

    git clone --bare https://github.com/<lecturer>/<team-repo>.git gallery-mirror
cd gallery-mirror
git push --mirror https://github.com/<you>/gallery-practice.git
cd ..

    Then delete the gallery-mirror folder. To work on the practice repo later, clone it like any other: git clone https://github.com/<you>/gallery-practice.git.

  3. In gallery-practice on GitHub, open Settings → Secrets and variables → Actions → New repository secret and add two secrets, TEST_DB_PASSWORD and TEST_DB_ROOT_PASSWORD. Choose your own values, letters and digits only.

The copy includes the team’s workflows, so a deploy-test run may appear straight away as Queued. It waits for your runner, and starts once you finish 2.7.

The practice repo is yours: you are its owner, so you can register runners and set secrets yourself. Its ci runs use your own account’s free Actions minutes.

2.1 Start the lab

  1. Sign in to AWS Academy and open the course your lecturer enrolled you in (Cloud Web Application Builder).
  2. Open the lab and click Start Lab. Wait until the dot next to AWS turns green.
  3. Click AWS to open the AWS console. Leave the region as the lab sets it (usually N. Virginia, us-east-1).
  4. In the lab window, open AWS Details and click Download PEM. Save labsuser.pem somewhere you can find it.
WarningBudget

Your lab account has a fixed budget. A t3.medium costs a few cents an hour while it is running. Stop the instance when your team is finished for the week, and never create more than this lesson and the next one ask for.

2.2 Create a security group

EC2 → Security Groups → Create security group:

  • Name: gallery-web
  • Description: Gallery app servers
  • VPC: the lab’s default VPC
  • Inbound rules:
    • SSH, port 22, source My IP
    • HTTP, port 80, source Anywhere-IPv4
  • Outbound rules: leave the default (All traffic to 0.0.0.0/0). The server needs it to download packages and reach GitHub.

Do not open port 3306. The database runs on the same server as the app and is never reachable from outside it.

2.3 Launch the instance

EC2 → Instances → Launch instances:

Setting Value
Name gallery-test
Image (AMI) Ubuntu Server 24.04 LTS, 64-bit (x86)
Instance type t3.medium. A Maven build, the app and MySQL need about 4 GB of memory; smaller types run out
Key pair vockey
Network settings → Edit Subnet: a public subnet. Auto-assign public IP: Enable. Security group: Select existing → gallery-web
Storage 20 GiB, gp3

Click Launch instance, then open the instance and wait until Instance state is Running and Status checks pass. Copy its Public IPv4 address.

Important

If the instance has no public IPv4 address, or sits in a private subnet, it cannot reach the internet and every later step fails. Terminate it and launch again with the settings above.

2.4 Connect over SSH

  • Windows (PowerShell)
  • macOS / Linux

The first time only, restrict the key file to your user, or SSH refuses to use it:

icacls labsuser.pem /inheritance:r /grant:r "$($env:USERNAME):R"

Then connect:

ssh -i labsuser.pem ubuntu@<public-ip>
chmod 400 labsuser.pem
ssh -i labsuser.pem ubuntu@<public-ip>

Type yes when asked about the host fingerprint. The prompt changes to ubuntu@ip-…, which means you are on the server. Every command from here to 2.7 runs on the server.

2.5 Check the server can reach the internet

curl -4 -m 5 -sI https://github.com | head -1

You should see HTTP/2 200. If the command hangs and prints nothing, the server has no internet access: check it has a public IP, that its subnet’s route table sends 0.0.0.0/0 to an igw- target, and that gallery-web still allows all outbound traffic.

2.6 Install Docker

sudo apt-get update
sudo apt-get install -y docker.io
sudo usermod -aG docker ubuntu
exit

exit logs you out so the new group membership applies. Reconnect with the same ssh command, then check:

docker run --rm hello-world

It should print Hello from Docker! without needing sudo.

NoteDatabase passwords

You do not create these on the server. They are the two repository secrets you added in 2.0, TEST_DB_PASSWORD and TEST_DB_ROOT_PASSWORD. The first deployment writes them to ~/gallery/db.env on this server (step 2.8 shows how), and every later deployment reads them from there. Secrets never go into Git, and GitHub hides them if they appear in a log.

If you skipped adding them, do it now. If this server already has a ~/gallery/db.env from earlier, the deployment keeps it.

2.7 Install the GitHub runner

The runner is a small program that asks GitHub for jobs and runs them on this server.

Get a registration token from your practice repo. On GitHub, open gallery-practice → Settings → Actions → Runners → New self-hosted runner, choose Linux, and copy the token from the ./config.sh line in the Configure block. It expires after one hour.

Download the latest runner:

mkdir ~/actions-runner && cd ~/actions-runner
RUNNER_VERSION=$(curl -s https://api.github.com/repos/actions/runner/releases/latest | grep -oP '"tag_name": "v\K[^"]+')
curl -sL -o runner.tar.gz https://github.com/actions/runner/releases/download/v${RUNNER_VERSION}/actions-runner-linux-x64-${RUNNER_VERSION}.tar.gz
tar xzf runner.tar.gz

Register it with your practice repo, using its URL without .git, and the token:

./config.sh --url https://github.com/<you>/gallery-practice --token <TOKEN> --name gallery-test --labels test --unattended

It ends with √ Settings Saved. The runner gets the labels self-hosted, Linux, X64 and test. The test label is how the deploy workflow finds this server.

If it stops with a message about missing .NET dependencies, run sudo ./bin/installdependencies.sh and then the config.sh command again.

Install the runner as a service, so it starts again whenever the instance starts:

sudo ./svc.sh install
sudo ./svc.sh start
sudo ./svc.sh status

The status shows active (running) and, near the bottom, Listening for Jobs. Your practice repo’s runner list (Settings → Actions → Runners) shows it as Idle.

Warning

Do not run ./run.sh. It runs the runner only while your SSH session stays open; the service replaces it.

2.8 The workflows

Two workflow files in .github/workflows tell GitHub what to do. Your practice repo already contains both, copied from your team repo, so there is nothing to add. Read them and the explanations, so you know what your server is about to do.

.github/workflows/ci.yml runs on GitHub’s own machines for every pull request, and puts a red cross on the pull request if the build or a test fails. GitHub still lets you merge it, so the team rule is never to merge while ci is red (step 4.7):

name: ci
on:
  pull_request:
    branches: [develop, main]
jobs:
  build:
    runs-on: ubuntu-latest
    services:
      db:
        image: mysql:8.4
        env:
          MYSQL_ROOT_PASSWORD: rootpass
          MYSQL_DATABASE: idm3project2024
          MYSQL_USER: gallery
          MYSQL_PASSWORD: gallerypass
        ports: ["3306:3306"]
        options: --health-cmd="mysqladmin ping -h localhost" --health-interval=5s --health-retries=20
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-java@v5
        with:
          distribution: temurin
          java-version: '17'
          cache: maven
      - run: chmod +x mvnw
      - name: Download Maven
        env:
          MVNW_VERBOSE: "true"
        run: |
          for i in 1 2 3; do
            ./mvnw -B -v && exit 0
            echo "Download failed, retrying in 15 seconds"; sleep 15
          done
          exit 1
      - run: ./mvnw -B verify
  • services: db starts an empty MySQL next to the build, with the same names and passwords as your laptop’s docker-compose.yml, on localhost:3306. The app’s test starts the whole application, including its database connection, so it needs a database to connect to. These are throwaway passwords for a database that exists only for the length of the build.
  • The Download Maven step fetches Maven before the build and retries up to three times, because Maven Central sometimes refuses a download from GitHub’s busy shared machines. MVNW_VERBOSE makes the log show the real error if all three attempts fail.

.github/workflows/deploy-test.yml runs on the server labelled test every time something is merged into develop:

name: deploy-test
on:
  push:
    branches: [develop]
  workflow_dispatch:
concurrency: deploy-test
permissions:
  contents: read
  pull-requests: read
jobs:
  deploy:
    runs-on: [self-hosted, test]
    steps:
      - uses: actions/checkout@v7
      - name: Find the pull request
        env:
          GH_TOKEN: ${{ github.token }}
        run: |
          INFO=$(curl -fsS -H "Authorization: Bearer $GH_TOKEN" -H "Accept: application/vnd.github+json" \
              "https://api.github.com/repos/$GITHUB_REPOSITORY/commits/$GITHUB_SHA/pulls" \
            | python3 -c 'import json,sys; prs=[p for p in json.load(sys.stdin) if p.get("merged_at")]; print("PR #%d: %s" % (prs[0]["number"], " ".join(prs[0]["title"].split())) if prs else "")' \
            || true)
          [ -n "$INFO" ] || INFO="develop at ${GITHUB_SHA::7}"
          echo "Footer will show: $INFO"
          echo "BUILD_INFO=$INFO" >> "$GITHUB_ENV"
      - name: Build the image
        run: |
          chmod +x mvnw
          docker build -t gallery:test .
      - name: Write db.env from the repository secrets
        env:
          DB_PASSWORD: ${{ secrets.TEST_DB_PASSWORD }}
          DB_ROOT_PASSWORD: ${{ secrets.TEST_DB_ROOT_PASSWORD }}
        run: |
          if [ -f ~/gallery/db.env ]; then
            # The database keeps the passwords it was first created with, so an existing file wins.
            if [ -n "$DB_PASSWORD" ] && ! grep -qxF "MYSQL_PASSWORD=$DB_PASSWORD" ~/gallery/db.env; then
              echo "::warning::~/gallery/db.env on the server does not match the TEST_DB_PASSWORD secret. The server's file is used. Reset the test database to switch (course step 5.4)."
            fi
            echo "Using the existing ~/gallery/db.env"
            exit 0
          fi
          if [ -z "$DB_PASSWORD" ] || [ -z "$DB_ROOT_PASSWORD" ]; then
            echo "::error::Add the TEST_DB_PASSWORD and TEST_DB_ROOT_PASSWORD repository secrets (course step 2.6)."
            exit 1
          fi
          case "$DB_PASSWORD$DB_ROOT_PASSWORD" in
            *[!A-Za-z0-9]*) echo "::error::The database passwords must be letters and digits only."; exit 1 ;;
          esac
          mkdir -p ~/gallery
          umask 077
          printf 'MYSQL_DATABASE=idm3project2024\nMYSQL_USER=gallery\nMYSQL_PASSWORD=%s\nMYSQL_ROOT_PASSWORD=%s\n' \
            "$DB_PASSWORD" "$DB_ROOT_PASSWORD" > ~/gallery/db.env
          echo "Created ~/gallery/db.env"
      - name: Start the database
        run: |
          docker network create gallery 2>/dev/null || true
          if [ -z "$(docker ps -q -f name=^gallery-db$)" ]; then
            mkdir -p ~/gallery/initdb
            cp idm3project2024.sql ~/gallery/initdb/01-idm3project.sql
            docker rm -f gallery-db 2>/dev/null || true
            docker run -d --name gallery-db --network gallery --restart unless-stopped \
              --env-file ~/gallery/db.env \
              -v gallery-dbdata:/var/lib/mysql \
              -v ~/gallery/initdb:/docker-entrypoint-initdb.d:ro \
              --health-cmd "mysqladmin ping -h localhost" --health-interval 5s \
              mysql:8.4
          fi
          for i in $(seq 1 60); do
            if [ "$(docker inspect -f '{{.State.Health.Status}}' gallery-db)" = healthy ]; then echo "Database is up"; exit 0; fi
            sleep 2
          done
          docker logs gallery-db
          exit 1
      - name: Replace the running container
        run: |
          set -a; . ~/gallery/db.env; set +a
          docker rm -f gallery || true
          docker run -d --name gallery --network gallery --restart unless-stopped \
            -p 80:8080 -e SPRING_PROFILES_ACTIVE=test -e APP_BUILD_INFO="$BUILD_INFO" \
            -e SPRING_DATASOURCE_URL="jdbc:mysql://gallery-db:3306/$MYSQL_DATABASE" \
            -e SPRING_DATASOURCE_USERNAME="$MYSQL_USER" \
            -e SPRING_DATASOURCE_PASSWORD="$MYSQL_PASSWORD" \
            gallery:test
      - name: Wait for the app to answer
        run: |
          for i in $(seq 1 60); do
            if curl -fs http://localhost/MainGallery/Login > /dev/null; then echo "App is up"; exit 0; fi
            sleep 2
          done
          docker logs gallery
          exit 1
      - name: Show the site address
        run: |
          # Ask AWS for this instance's public IP. It changes each time the lab restarts.
          TOKEN=$(curl -fsS --max-time 5 -X PUT http://169.254.169.254/latest/api/token \
            -H "X-aws-ec2-metadata-token-ttl-seconds: 60" || true)
          IP=$(curl -fsS --max-time 5 -H "X-aws-ec2-metadata-token: $TOKEN" \
            http://169.254.169.254/latest/meta-data/public-ipv4 || true)
          SITE=${IP:+http://$IP/MainGallery/HomePage}
          {
            echo "### Test site deployed"
            echo "- Site: ${SITE:-no public IP found}"
            echo "- Footer: $BUILD_INFO"
            echo "- Database: $(grep '^MYSQL_DATABASE=' ~/gallery/db.env | cut -d= -f2), user $(grep '^MYSQL_USER=' ~/gallery/db.env | cut -d= -f2)"
          } >> "$GITHUB_STEP_SUMMARY"
          echo "Site: ${SITE:-no public IP found}"
      - name: Remove old images
        run: docker image prune -f

What it does, step by step:

  • runs-on: [self-hosted, test] picks the runner with both labels: your test server.
  • Find the pull request asks the GitHub API which merged pull request produced this commit on develop, and saves a label such as PR #9: Add team cards. If someone pushed to develop directly, the label is develop at plus the commit’s short ID. permissions: pull-requests: read lets the workflow’s token make that call.
  • Build the image builds the app inside Docker from the repo’s Dockerfile: compile with the JDK, then copy the jar onto a smaller Java runtime image. chmod +x mvnw makes the Maven wrapper executable, in case it was committed from Windows without that permission.
  • Write db.env from the repository secrets runs only when ~/gallery/db.env does not exist yet. It writes the database name (idm3project2024), the user (gallery) and the two passwords from the repo’s secrets into that file, readable only by ubuntu. If the file is already there, it is kept: MySQL sets its passwords only when it first creates the database, so replacing them later would lock the app out. If the file does not match the secret, the run shows a warning.
  • Start the database creates a private Docker network called gallery. The first time, it starts a MySQL container called gallery-db on that network, using the names and passwords in ~/gallery/db.env, and loads idm3project2024.sql into it. The data lives in a Docker volume, gallery-dbdata. On every later deploy the database is already running, so the step leaves it alone and your test data survives.
  • Replace the running container starts the app on the same network and maps port 80 on the server to the app’s port 8080. It overrides the database settings in application.properties, which point at localhost: inside a container, localhost is the container itself. Instead the app gets gallery-db, the database container’s name on the network, plus the user and password from db.env. -e APP_BUILD_INFO passes the footer label, and --restart unless-stopped starts the app again whenever the instance restarts.
  • Wait for the app to answer checks the login page, which is public, for up to two minutes, and prints the app’s log if it never answers.
  • Show the site address asks AWS for the server’s public IP and adds a summary to the run: a link to the site, the footer label, and the database name and user. Passwords are never shown.
NoteHow this matches your laptop

Locally, docker compose up does the same job: docker-compose.yml starts a db service and sets SPRING_DATASOURCE_URL to jdbc:mysql://db:3306/idm3project2024. On the server, the workflow does it with docker run commands, and the database is called gallery-db.

NoteHow the footer works

application.properties has app.build-info=${APP_BUILD_INFO:local dev}, so the label comes from the APP_BUILD_INFO environment variable and is local dev on your laptop. BuildInfoAdvice.java adds it to every page, and templates/fragments/footer.html displays it. Pages show it by including the footer fragment:

<footer th:replace="~{fragments/footer :: footer}"></footer>

Add that line to every new page you create, just before </body>.

2.9 Check the first deployment

  1. If no deploy-test run is waiting, start one: in gallery-practice, open Actions → deploy-test → Run workflow and choose develop.
  2. Click the run. The first build takes several minutes while Maven downloads its dependencies. Write db.env from the repository secrets prints Created ~/gallery/db.env, and Start the database ends with Database is up.
  3. When it is green, the run’s summary page shows Test site deployed with a link to the site. Click it.
  4. Check the home page lists the sample projects and showcases, and that a test login from step 1.5 works.

The footer shows develop at and the commit’s short ID, because your practice repo has no pull requests of its own yet. To see a pull request in the footer, make a small change on a branch of gallery-practice, open a pull request into develop there, and merge it.

TipCheckpoint

Your practice site loads from the link in the run’s summary, with the sample data showing. Stop the instance when you have finished, to save your lab budget.

Between lab sessions

  • When the lab ends, the instance may be stopped. When you start the lab again, start the instance if it is not already running. The runner service, the database and the app start by themselves. The app may restart once while MySQL is still starting; that is expected.
  • The public IP changes each time the instance starts. The next deployment’s summary shows the new address; to get it without a merge, open Actions → deploy-test → Run workflow. You can also find it in the EC2 console. Update it on your board.
  • While the instance is stopped, deploy jobs wait in the queue as Queued. They run once the instance is back, or fail after 24 hours.
