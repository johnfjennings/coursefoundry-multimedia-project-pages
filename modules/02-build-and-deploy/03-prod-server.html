3. Create the prod server on AWS

Author

Mr. John Jennings

Who: a different driver from step 2, in their own AWS Academy lab. Spreading the servers across two accounts shares the cost between two budgets. Goal: a second EC2 instance, with a runner labelled prod, which deploys only release tags on main.

The prod server is built exactly like the test server. Only four things differ:

Test server (step 2) Prod server (this step)
Instance name gallery-test gallery-prod
Runner name and label gallery-test, test gallery-prod, prod
Deploys when A merge into develop A tag such as v0.1.0 is pushed on main
Spring profile test prod

3.1 Build the server

Follow step 2 from 2.1 to 2.6, with these changes:

  • Start the lab in your own account. Create the gallery-web security group there too (2.2), since security groups belong to one account.
  • Name the instance gallery-prod (2.3).

Check docker run --rm hello-world works before moving on.

3.2 Install the runner

Ask your lecturer for a new registration token; tokens expire after an hour. Then on the prod server:

mkdir ~/actions-runner && cd ~/actions-runner
RUNNER_VERSION=$(curl -s https://api.github.com/repos/actions/runner/releases/latest | grep -oP '"tag_name": "v\K[^"]+')
curl -sL -o runner.tar.gz https://github.com/actions/runner/releases/download/v${RUNNER_VERSION}/actions-runner-linux-x64-${RUNNER_VERSION}.tar.gz
tar xzf runner.tar.gz
./config.sh --url https://github.com/<lecturer>/<team-repo> --token <TOKEN> --name gallery-prod --labels prod --unattended
sudo ./svc.sh install
sudo ./svc.sh start
sudo ./svc.sh status

Check for active (running) and Listening for Jobs.

NoteHow “polling for tags” works

The runner keeps a connection open to GitHub and asks “any jobs for prod?”. GitHub only creates such a job when someone pushes a tag beginning with v. Until then, the prod server does nothing, however many times develop changes.

3.3 Add the prod workflow

On your laptop, through a pull request into develop:

git switch develop
git pull
git switch -c feature/add-prod-pipeline

Create .github/workflows/deploy-prod.yml:

name: deploy-prod
on:
  push:
    tags: ['v*']
concurrency: deploy-prod
jobs:
  deploy:
    runs-on: [self-hosted, prod]
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - name: Check the tag is on main
        run: |
          if ! git merge-base --is-ancestor "$GITHUB_SHA" origin/main; then
            echo "Tag ${GITHUB_REF_NAME} is not on main. Only tag commits on main."
            exit 1
          fi
      - name: Build the image
        run: |
          chmod +x mvnw
          docker build -t gallery:${GITHUB_REF_NAME} .
      - name: Replace the running container
        run: |
          docker rm -f gallery || true
          docker run -d --name gallery --restart unless-stopped \
            -p 80:8080 -e SPRING_PROFILES_ACTIVE=prod gallery:${GITHUB_REF_NAME}
      - name: Wait for the app to answer
        run: |
          for i in $(seq 1 30); do
            if curl -fs http://localhost/login > /dev/null; then echo "Release ${GITHUB_REF_NAME} is up"; exit 0; fi
            sleep 2
          done
          docker logs gallery
          exit 1

How it differs from deploy-test.yml:

  • on: push: tags: ['v*'] runs it for tags such as v0.1.0, and never for branch pushes.
  • fetch-depth: 0 downloads the full history, so the next step can see main.
  • Check the tag is on main stops the deployment if someone tags a commit that has not been through a release pull request.
  • The image is named after the tag, e.g. gallery:v0.1.0. Older release images stay on the server, which makes rolling back possible (step 7).

Commit, push and open a pull request into develop. When ci is green, a teammate approves and merges it.

Merging it into develop does not deploy anything to prod: there is no tag yet, and the file only reaches main at your first release (step 6).

TipCheckpoint

Two servers, each with a runner listening: gallery-test (label test) and gallery-prod (label prod). http://<prod-ip>/ does not answer yet, which is expected until step 7.
