Build and deploy: overview

Author

Mr. John Jennings

In this module your team takes the Gallery skeleton from your laptops to two servers on AWS, which your lecturer runs for your team: a test server that always runs the latest develop, and a prod server that runs the latest release tag on main.

The whole process

Environment Where Runs Updated when Footer shows
dev Your laptop Whatever branch you have checked out You run it local dev
test EC2 instance with the label test The latest commit on develop A PR is merged into develop PR #9: Add team cards
prod EC2 instance with the label prod The latest release tag, e.g. v0.1.0 A tag is pushed on main Release v0.1.0

Each EC2 instance runs a GitHub self-hosted runner. The runner connects out to GitHub and asks for jobs; GitHub never connects in. That is why the servers only need port 80 open to the world, and why it does not matter that their public IP changes between lab sessions.

The steps

  1. Clone the team repo and run it locally
  2. Optional: create a test server on AWS
  3. Optional: create a prod server on AWS
  4. Feature branches and pull requests
  5. Check the change on the test server
  6. Release: pull request to main and tag
  7. Check the prod deployment

Step 1 is done by every team member, and steps 4 to 7 by the whole team.

Steps 2 and 3 are optional. Your lecturer has already built your team’s test and prod servers, so your team can deploy without them. Do them if you want to learn how a server, Docker and a GitHub runner are set up. You build your own servers for your own practice copy of the repo, so nothing you do there affects your team’s servers.

Finding your team’s sites

Your lecturer runs both servers. You never need to log in to them, and you do not need to remember their addresses: every deployment posts the site’s current address on GitHub.

  1. In your team repo, open the Actions tab.
  2. On the left, click deploy-test for the test site, or deploy-prod for the prod site.
  3. Click the newest run with a green tick.
  4. The run’s summary page shows, below the job graph, Test site deployed (or Release v0.1.0 deployed) with a Site link. Click it.
TipIf the link does not answer

A server gets a new IP address whenever it restarts, for example between lab sessions, so an old summary can point at an old address. Get a fresh one:

  • Test: Actions → deploy-test → Run workflow, choose develop, and wait for the run to finish. It deploys develop again and posts the current address.
  • Prod: open the newest deploy-prod run and click Re-run all jobs. It deploys the same release again and posts the current address.

If the run stays Queued, the server is stopped: tell your lecturer.

What you need

  • A GitHub account, with the invitation to your team repo accepted
  • JDK 17, Docker Desktop and Git on your laptop
  • For the optional steps 2 and 3 only: access to the AWS Academy course your lecturer has enrolled you in, and an SSH client (the ssh command in PowerShell, Terminal or Git Bash)
NoteFor the lecturer: before class

  1. Create one private repo per team from the Gallery skeleton on your GitHub account, and add each student as a collaborator with Write access.

  2. Branch protection (optional). Without it, ci.yml still runs on every pull request and shows a red cross when the build fails, but GitHub does not stop anyone merging, merging without a review, or pushing straight to develop or main. The lessons treat a green ci, one approval and no direct pushes as team rules (step 4.7), which you can check in each pull request’s history. To have GitHub enforce them, protect develop and main: require a pull request, one approval, and the build status check. On a personal account, branch protection for private repos needs GitHub Pro (free for teachers through GitHub Education).

  3. Merge settings. In Settings → General → Pull Requests, allow both squash merging (feature pull requests, step 4) and merge commits (release pull requests, step 6).

  4. Servers and runners. You run a test and a prod server for each team, built as in steps 2 and 3. Register each server’s runner in the team repo with the label test or prod (Settings → Actions → Runners → New self-hosted runner). Students who do the optional steps work in their own practice repo, where they are the owner and can register runners and set secrets themselves. They must never register a runner in a team repo: a second runner with the same label would take some of the team’s deployments.

  5. Actions minutes. ci.yml runs on GitHub’s own runners and uses your account’s included minutes for private repos. The deploy workflows run on the teams’ EC2 runners and use none.

  6. Workflows. Team repos created from the template contain ci.yml and deploy-test.yml. Add deploy-prod.yml (step 3.3) to each team repo before its first release, or the release tag deploys nothing.

  7. Check the skeleton builds on Linux. mvnw should be committed as executable (git update-index --chmod=+x mvnw), and .mvn/wrapper/maven-wrapper.properties must be present. The workflows run chmod +x mvnw as a safety net, but cannot replace a missing wrapper file.

  8. Footer build label. The footer needs four things in the skeleton: app.build-info: ${APP_BUILD_INFO:local dev} in application.yml, web/BuildInfoAdvice.java, templates/fragments/footer.html, and the fragment included on each page. Group00’s pull request #9 adds all four and can be copied into the skeleton. Without them the app still runs, but the footer label does not appear.

  9. Database secrets. Each team repo needs four repository secrets, which the deploy workflows write to ~/gallery/db.env on each server: TEST_DB_PASSWORD, TEST_DB_ROOT_PASSWORD, PROD_DB_PASSWORD and PROD_DB_ROOT_PASSWORD. Only the repo owner can set them. Use letters and digits only. This generates random ones, keeps a copy in a local file (GitHub cannot show a secret again) and sets them:

    repo=<owner>/<team-repo>
for s in TEST_DB_PASSWORD TEST_DB_ROOT_PASSWORD PROD_DB_PASSWORD PROD_DB_ROOT_PASSWORD; do
  v=$(openssl rand -hex 16)
  echo "$s=$v" >> "${repo#*/}-db-secrets.txt"
  gh secret set "$s" -R "$repo" --body "$v"
done

    Keep the .txt file outside any Git repo. Or add each one in Settings → Secrets and variables → Actions → New repository secret. A server’s db.env is written only on its first deployment, so set the secrets before a server’s first deployment.
